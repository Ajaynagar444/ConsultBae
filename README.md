# ConsultBae — AI Automation Take-Home

Merging three messy product databases into one clean record set, then
automating on top of it.

> **Status:** database foundation and raw CSV ingestion working.
> 105 source rows load into `raw_record`. Normalisation, matching and the golden
> layer are next. See [Roadmap](#roadmap).

---

## Purpose

ConsultBae runs several products — recruitment gigs, CBNexus, and internal
automations — each with its own database. This repo takes three CSV exports of
those systems, with overlapping people and deliberately inconsistent data, and:

1. merges them into one PostgreSQL database where each real person is **one**
   record,
2. drives a no-code automation on top of that database,
3. collects audio submissions from gig workers and extracts their technical
   properties,
4. reports every data-quality problem found along the way.

No single ID field is shared across all three files. Working out how to match
people — and knowing when *not* to — is the core of the exercise. The full
evidence base is in **[docs/data-profile.md](docs/data-profile.md)**.

## Headline findings from profiling

Measured before writing any code, so the design answers real problems rather
than imagined ones:

- **105 lines → 102 usable rows → 56 unique people.**
- Source 1 is the **only** file with both email *and* phone. Source 2 has email
  only, source 3 has phone only — so source 1 is the bridge, and anyone in
  sources 2 and 3 but not 1 has no shared key at all.
- **16 classes of data-quality problem**, including a column-shifted row that
  hides a duplicate, an embedded header row, and two columns that silently mix
  two units each.
- **Two planted traps:** an `Arjun Mehta` who cannot be resolved from the data
  (left unmerged, queued for review) and a `Deepak Nair` who is two different
  people (a naive name match would fuse them).

Details, counts and the reasoning behind every decision:
**[docs/data-profile.md](docs/data-profile.md)**.

## Planned architecture

A three-layer **raw → staging → golden** pipeline. The raw layer is append-only,
so the original data is never lost and every merged record can be traced back to
the exact source lines that produced it.

```
  data/raw/*.csv                (committed verbatim, never edited)
        │
        ▼  ingest.py
  raw_record (jsonb)            append-only, one row per source line
        │
        ▼  repair.py + normalize.py
  staged_person                 cleaned; bad rows quarantined, not deleted
        │
        ▼  match.py + survivorship.py
  person + person_email         56 golden records
  person_phone + person_skill
  person_source_link            provenance: which source lines, matched how
  data_issue / match_review     generated Task 4 report + human review queue
        │
        ▼
  n8n (Task 2)                  reads and writes the same database
  audioapp (Task 3)             audio_submission → person via the same matcher
```

### Key decisions

- **PostgreSQL 18, running natively.** `jsonb` for lossless raw preservation,
  real constraints and enums, and a first-class Postgres node in n8n so Task 2
  can query and write back. A server was already installed on this machine, so
  Docker would buy nothing here while costing several GB on a nearly full disk.
  The compose file stays in the repo as the portable path for other machines.
- **Raw SQL over `psycopg`, no ORM.** ~100 rows and a bespoke schema — an ORM
  would add a layer to defend for no benefit.
- **`normalize.py` is pure functions with no database access.** Every
  normalisation rule becomes a one-line unit test.
- **Deterministic matching before fuzzy.** Exact email, then exact phone, then a
  *guarded* name-only pass. Name is a blocking key, never a deciding one.
- **Ambiguity is surfaced, not resolved by guessing.** Unresolvable matches go
  to a `match_review` queue with a stated reason.
- **`data_issue` rows are generated by the pipeline**, so the Task 4 report is
  produced from the database rather than hand-written.

## Setup

**Prerequisites:** PostgreSQL 18 (running locally as service
`postgresql-x64-18`), Python 3.11+, and `ffmpeg`/`ffprobe` on PATH (Task 3 only).

```powershell
# 1. Create the project role and databases. The app password is passed in as a
#    psql variable, so no credential is ever stored in the repo.
$env:PGPASSWORD = '<postgres superuser password>'
& 'C:\Program Files\PostgreSQL\18\bin\psql.exe' -U postgres `
    -v app_password="'<choose an app password>'" -f scripts/init_db.sql

# 2. Configuration
Copy-Item .env.example .env     # set POSTGRES_PASSWORD to the app password above

# 3. Python environment
python -m venv .venv
.\.venv\Scripts\Activate.ps1    # bash/WSL: source .venv/bin/activate
pip install -r requirements.txt

# 4. Create the schema
python scripts/migrate.py

# 5. Verify it
python scripts/db_check.py
```

> **Note on the password.** If it contains `@`, `/`, `:` or `#`, those must be
> percent-encoded inside `DATABASE_URL` (`@` → `%40`) even though
> `POSTGRES_PASSWORD` takes them literally. An unencoded `@` makes the driver
> read everything after it as the hostname, and the resulting error points
> nowhere near the real cause.

## Running

```powershell
python scripts/migrate.py --status   # what is applied, changes nothing
python scripts/migrate.py --reset    # drop and rebuild the schema

python -m src.pipeline.ingest             # load the 3 CSVs into raw_record
python -m src.pipeline.ingest --dry-run   # parse and report, write nothing
python -m src.pipeline.ingest --run-id 2  # re-ingest into an existing run
python -m src.pipeline.ingest --log-format json
pytest                               # test suite (47 tests)
python -m src.audioapp.app           # Task 3 - not implemented yet
```

Migrations are checksum-tracked in `schema_migration`: re-running is a no-op,
and editing a file that has already been applied is refused rather than silently
ignored. Tests run against a separate `consultbae_test` database, so a test run
can never touch working data.

The pipeline is designed to be **idempotent** — re-running it is safe and
produces the same 56 records, which also makes it easy to demo live.

### Running without a local PostgreSQL

`docker-compose.yml` is an optional portable path for anyone cloning this repo
who does not have PostgreSQL installed. It publishes **5433**, not 5432, so it
can coexist with a native server:

```bash
# in .env: POSTGRES_PORT=5433
docker compose up -d && docker compose ps
```

Task 2 adds n8n to that compose file. On a machine without Docker, n8n also runs
via `npx n8n` or the free n8n cloud trial — the assignment permits self-hosted
or cloud.
